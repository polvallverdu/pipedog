When building real-time AI applications two things matter to monitor: **performance** (latency),
which shapes the user experience, and **usage** (LLM tokens, TTS characters), which drives cost.
pipedog ports Pipecat's built-in metrics for both.

## Enabling metrics

Metrics are switched on through `PipelineParams` when creating the worker:

<include cwd>snippets/metrics.ts#enable</include>

With `enableMetrics`, services report:

| Metric | Description |
|---|---|
| TTFB | Time to first byte, in seconds. |
| TTFA | Time to first audio, in seconds (TTS services). |
| TTFAT | Time to first answer token, in seconds (LLM services). |
| Processing time | Time the service took to respond, in seconds. |
| Text aggregation | Time from the first LLM token to the first complete sentence (TTS services). |

With `enableUsageMetrics`, services report LLM prompt/completion tokens and TTS characters. Usage
metrics are per interaction, not running totals.

- `reportOnlyInitialTtfb: true` reports only the first TTFB measurement of each service.
- By default the worker sends an initial `MetricsFrame` with zero values for every service when
  the pipeline starts; `sendInitialEmptyMetrics: false` turns that off.

## Capturing metrics data

Every measurement travels as a `MetricsFrame` (a system frame) whose `data` is a list of
`MetricsData` objects from `@pipedog/core/metrics/metrics`:

- `TTFBMetricsData`, `TTFAMetricsData`, `TTFATMetricsData`
- `ProcessingMetricsData`, `TextAggregationMetricsData`
- `LLMUsageMetricsData` (its `value` is an `LLMTokenUsage`: `promptTokens`, `completionTokens`,
  `totalTokens`, cache and reasoning token counts)
- `STTUsageMetricsData`, `TTSUsageMetricsData`
- `TurnMetricsData`

All of them have `processor` (the name of the processor that produced the metric) and an
optional `model`. Read them with an **observer** such as `MetricsLogObserver` (above), or with a
custom processor placed after the services:

<include cwd>snippets/metrics.ts#capture</include>

Processors that generate metrics use the helpers on `FrameProcessor`: `startTtfbMetrics()` /
`stopTtfbMetrics()`, `startProcessingMetrics()` / `stopProcessingMetrics()`,
`startLlmUsageMetrics(tokens)`, `startTtsUsageMetrics(text)` and so on. They only report when
metrics are enabled, and `canGenerateMetrics()` tells the worker which processors to include in
the initial empty metrics.

To send TTFB and processing time to Sentry as transactions, see [Sentry metrics](/docs/concepts/sentry-metrics).

## Tracing (OpenTelemetry)

pipedog ports Pipecat's OpenTelemetry tracing: one trace per conversation, a span per turn, and
spans for the service calls in each turn. Span names, attributes and their hierarchy are the same
as upstream's, so dashboards and LLM-observability tools built for Pipecat traces (Langfuse,
Honeycomb, Grafana Tempo, Jaeger, ...) work unchanged.

Like upstream's `pipecat-ai[tracing]` extra, OpenTelemetry is optional:

- `@pipedog/core` has `@opentelemetry/api` as an **optional peer dependency**. Without it, core
  runs exactly the same, `isTracingAvailable()` is false and every tracing helper is a no-op.
- `@pipedog/tracing` brings the OpenTelemetry SDK, an OTLP/HTTP exporter and `setupTracing()`.

```bash
bun add @pipedog/tracing @opentelemetry/api
```

### Setup

Call `setupTracing()` once at startup, then turn tracing on per worker with `enableTracing`:

<include cwd>snippets/tracing.ts#setup</include>

`setupTracing({ serviceName, exporter, consoleExport })` matches upstream's
`setup_tracing(service_name, exporter, console_export)`. It sets the resource attributes
`service.name`, `service.instance.id` (`$HOSTNAME`) and `deployment.environment`
(`$ENVIRONMENT`, default `development`), adds a batch span processor for each exporter, and
registers the global tracer provider (which, as in Python, can only be set once per process). It
returns `false` if setup failed.

`@pipedog/tracing` re-exports `OTLPTraceExporter` (from `@opentelemetry/exporter-trace-otlp-http`,
which sends OTLP/HTTP JSON with `fetch` or `node:http`), `ConsoleSpanExporter`,
`InMemorySpanExporter` and the span processors. Any OpenTelemetry `SpanExporter` works. Pointing
it at a hosted backend is a matter of URL and headers:

### Names: pipedog by default, pipecat for compatibility

Span names and attribute keys are upstream's (see below). Two names that say which library made
the trace differ, so a pipedog bot can be told apart from a Pipecat one:

| | pipedog | Pipecat |
| --- | --- | --- |
| Tracer (instrumentation scope, `otel.scope.name`): service spans | `pipedog` | `pipecat` |
| Tracer: conversation and turn spans | `pipedog.turn` | `pipecat.turn` |
| Default `service.name` (when you don't pass `serviceName`) | `pipedog` | `pipecat` |

Always set your own `serviceName` in production: it should name your app, not the library.

**If anything filters on Pipecat's tracer names** (a dashboard, an alert, a query on
`otel.scope.name`, or a Python and a TypeScript bot reporting to the same place), switch them back
with `setTracerName("pipecat")`, or `tracerName: "pipecat"` in `setupTracing`. Do it at startup,
before a pipeline is created, because the turn tracer is fetched when its observer is built. Span
names (`conversation`, `turn`, `stt`, `llm`, `tts`) and attribute keys (`gen_ai.*`,
`metrics.ttfb`, ...) don't depend on this: they are the same either way.

### Spans and attributes

```
conversation                    conversation.id, conversation.type = "voice", + additionalSpanAttributes
└── turn                        turn.number, turn.type, conversation.id, turn.duration_seconds,
    │                           turn.was_interrupted, turn.user_bot_latency_seconds
    ├── stt                     gen_ai.provider.name, gen_ai.request.model, gen_ai.operation.name,
    │                           transcript, is_final, language, vad_enabled, metrics.ttfb,
    │                           metrics.audio_seconds, settings.*
    ├── llm                     gen_ai.provider.name, gen_ai.request.model, gen_ai.operation.name = "chat",
    │                           stream, input, output, tools, tool_count, tool_choice,
    │                           gen_ai.system_instructions, gen_ai.usage.input_tokens,
    │                           gen_ai.usage.output_tokens, metrics.ttfb, gen_ai.request.*, param.*
    └── tts                     gen_ai.provider.name, gen_ai.request.model, gen_ai.output.type = "speech",
                                voice_id, text, metrics.character_count, metrics.ttfb, settings.*
```

- The **conversation** span starts with the pipeline (`StartFrame`) and ends when the worker
  finishes; its id is `conversationId`, or a random UUID.
- A **turn** span covers one user turn and the bot's answer, as tracked by `TurnTrackingObserver`.
- **Service** spans are children of the current turn (or of the conversation, between turns).
  They come from the `tracedStt` / `tracedLlm` / `tracedTts` decorators (and `tracedGeminiLive`,
  `tracedOpenaiRealtime` for speech-to-speech services, whose spans are named after the operation:
  `llm_setup`, `llm_request`, `llm_response`, `llm_tool_call`, `llm_tool_result`) in
  `@pipedog/core/utils/tracing/service_decorators`. Provider packages apply them as upstream's
  services do, so a service shows up in traces once its package is ported.

The metrics described above are recorded on these spans (`metrics.ttfb`, token usage, character
counts), not as separate OpenTelemetry metrics: like Pipecat, pipedog has no OpenTelemetry metrics
exporter. Read `MetricsFrame`s with an observer if you need them as time series.

### Keeping content out of traces

Like Pipecat's, the spans carry what people said and what the model answered: `transcript`,
`text`, `input`, `output`, `gen_ai.system_instructions`, tool definitions. With sensitive data (health,
payments, anything personal) pass `redactContent` and the spans keep timings, ids and metadata only:

```ts
import { setupTracing } from "@pipedog/tracing";

setupTracing({ serviceName: "my-voice-bot", exporter, redactContent: true });
```

- String attributes are dropped unless their key is allowed. The default list
  (`DEFAULT_REDACTION_ALLOWED_ATTRIBUTES`) holds the non-content keys pipedog writes: the model,
  provider and operation (`gen_ai.*`), `voice_id`, `language`, `settings.model` / `voice` /
  `language`, `conversation.id`, `conversation.type`, `turn.type`, tool names. Numbers and booleans
  (`metrics.*`, token counts, `turn.*` durations) are kept on any key.
- Events keep their name and only `exception.type`; a recorded exception keeps its type but not
  its message or stack; a status keeps its code but not its message.
- `redactContent: { extraAllowedAttributes: ["app.tenant"] }` adds your own keys (for example from
  `additionalSpanAttributes`), `allowedAttributes` replaces the list, and `isAllowed(key, value)`
  decides on its own.

Redaction happens as each attribute is written, on the SDK's own span, so nothing reaches a span
processor or exporter. If you set up OpenTelemetry yourself, call `registerWithCore({ redactContent: true })`
instead; `redactTracer`, `redactTracerProvider` and `redactSpan` apply it to your own spans. Not in
upstream.
