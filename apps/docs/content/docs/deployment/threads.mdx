title: Calls in worker threads
description: When one event loop is enough for many calls, when local models need more threads, and how to run calls in worker threads on Bun, Node and Deno, with measured numbers.
---

A pipedog server runs every call in one process by default: each call is its own pipeline and
`PipelineWorker`, and they all share one event loop. This page is about when that stops being
enough, and what to do then.

## The model

An event loop runs one thing at a time. A call that uses cloud services spends almost all its time
waiting: for the next audio packet, for the STT's transcript, for the LLM's tokens, for the TTS's
audio. While it waits, the loop serves the other calls. Moving a 20 ms audio frame through a
pipeline costs tens of microseconds, so one loop serves hundreds of such calls.

CPU work is different. While the loop runs a model, nothing else on it runs: not the other calls'
audio, not their timers, not their WebSocket messages. Local models are the usual CPU work in a
voice bot:

- **Silero VAD** on every 32 ms of input: about 0.1–0.2 ms each, cheap but per frame.
- **Smart Turn** at each end of speech: about 100 ms (Whisper features and the model). While it
  runs, every other call on that loop waits about 100 ms.
- Local STT or TTS models (Whisper, Kokoro, Piper), noise filters, heavy resampling.

So the question is not how many calls a process holds, but how much CPU work lands on each event
loop. The benchmark below measures where that line is.

## Measured

Each call in the benchmark behaves like a voice bot without the network. Its input is a speech
recording (6.4 s, then 1.6 s of silence) in 20 ms frames at 16 kHz, queued on a timer as a transport
queues them. A fake STT emits a transcription every 8 s, a fake LLM answers 350 ms later with a few
tokens, and a fake TTS streams 2 s of audio in real time; pass-through processors stand where the
context aggregators would be. That is the **cloud-service bot**: the CPU profile of a bot whose
STT, LLM and TTS are network services. The **local-model bot** adds Silero VAD on every frame
(`VADProcessor`) and Smart Turn v3 at each end of speech, on `onnxruntime-node`.

Three ways to run the calls: all on **one thread**; spread round-robin over a **worker per core**
(12 here); and, for the local-model bot, all on one thread with **Smart Turn on workers** (a
`SmartTurnWorkerPool` of 11 threads, below).

**Latency** is from the time each input frame was due to its arrival at the end of the pipeline, so
time spent waiting for a busy loop counts. The **real-time budget is 20 ms at p99**: one frame. A
frame that waits longer than the next one takes to arrive means audio queues up behind the loop:
the VAD, turn detection and interruptions react late, and the bot's own audio leaves late. Smart Turn
sits after the measuring point, so a call's wait for its own turn decision (the same at any
concurrency) isn't counted; what is counted is how long it holds up the other calls.

The same calls are written against Pipecat, in one asyncio process and in one process per core
(multiprocessing: Python threads share the GIL, so processes are Python's equivalent of worker
threads). Pipecat runs Silero and Smart Turn on a thread executor per analyzer, and onnxruntime
releases the GIL while it runs, so its models don't block its event loop.

### What the numbers say

- **Cloud-service bots: one event loop serves a few hundred calls.** On one thread, Node kept 400
  calls within budget, Bun and Deno 200; Pipecat's asyncio loop kept 50. A worker per core kept
  every runtime within budget at 800 calls, the most measured, using about 3 of the 12 cores. Each
  call holds about 1–1.5 MB.
- **Inline local models: no number of calls is real-time.** Smart Turn runs for about 100 ms on the
  thread that calls it (Whisper features in JavaScript, then `onnxruntime-node`, whose `run()`
  executes on the calling thread). Every call on that event loop stalls meanwhile, even with one
  call per loop, so worker threads alone don't fix it: with a worker per core, p99 stays at
  70–110 ms at every level. Silero VAD on every frame is cheap by comparison.
- **Smart Turn on worker threads fixes it.** With every call on one thread and Smart Turn's
  predictions on a pool of worker threads (`SmartTurnWorkerPool`, below), one Node thread kept
  100 local-model calls within budget, and Bun and Deno 50. The limit is then the calls' own
  thread (pipelines, Silero VAD, the transport), so many more calls need several of those threads
  too, each with the pool.
- **Pipecat** runs both models on thread executors, so its loop doesn't wait for them: 25
  local-model calls in one process and 100 with a process per core. It loads a Silero and a Smart
  Turn session per call (about 40 MB a call), where pipedog shares one session per thread.

One run per level, 6 s each: a lone ✗ below a series' maximum (Bun, one thread, 100 cloud-service
calls) is a one-off stall; that point measured 5 ms when run again.

## Which setup

| Bot | Setup |
|---|---|
| Cloud STT, LLM and TTS | Many calls per process, on one event loop. Scale out with more processes behind a load balancer before threads; past a few hundred calls per process, a worker per core. |
| Local Silero VAD + Smart Turn | Calls on the main thread (or a few worker threads), Smart Turn on a `SmartTurnWorkerPool`. Or run turn detection as a service (`HttpSmartTurnAnalyzer`) and keep the bot I/O-bound. |
| Local STT / TTS models (Whisper, Kokoro, Piper) | One call per worker thread, or a few: a model run blocks everything on its thread. |
| Cloudflare Workers | One Durable Object per call. See [Cloudflare Workers](/docs/deployment/cloudflare-workers). |

Several processes behind a load balancer (one per core, or one per container) are the simplest
scale-out on any runtime: nothing is shared, a crash takes down only its own calls, and the same
server code runs unchanged. Worker threads share one process's memory (one copy of the runtime and
the code) and start faster, but one process failure ends all its calls.

## Getting a connection to a worker

A socket belongs to the thread that accepted it, and can't be moved to another. So either each
worker accepts its own connections, or the main thread accepts them and forwards their messages.

| Option | Runtimes | Trade-off |
|---|---|---|
| Each worker runs its own server on a shared port (`reusePort`) | Bun, Deno, on Linux | Simplest; the kernel balances new connections, not load. macOS and Windows don't balance them. |
| Processes share a port (`node:cluster`) | Node | Processes, not threads: more memory, full isolation. |
| One port per worker, a proxy in front | All | Works everywhere; the proxy (nginx, a load balancer) does the balancing. |
| The main thread accepts, forwards messages to a worker | All, any OS | You choose the worker per call (least busy); every message crosses threads once each way (`postMessage`, with the audio transferred, not copied). |

WebRTC is the same story: the peer connection, and its UDP sockets, live in the thread that
created it, so post the offer to a worker and create the connection there. That path isn't covered
by this page's examples.

each server runs the same bot (`src/bot.ts`: Silero, Smart Turn, OpenAI services, protobuf frames

## Smart Turn on worker threads

`SmartTurnWorkerPool` keeps the Smart Turn model in a few worker threads and sends each prediction
to the least busy one. `pool.analyzer()` is a `LocalSmartTurnAnalyzerV3` (the same buffering and
parameters) whose predictions run there; one pool serves every call in the process:

```ts
import { SmartTurnWorkerPool } from "./smart_turn_pool.ts";
import { spawnThread } from "./threads.ts";

const smartTurn = new SmartTurnWorkerPool({
  size: 4,
  spawn: () => spawnThread(new URL("./smart_turn_thread.ts", import.meta.url)),
});

// In each call:
new TurnAnalyzerUserTurnStopStrategy({ turnAnalyzer: smartTurn.analyzer() });
```

`runBot(connection, { smartTurn })` in the example does this. The audio of each prediction (up to
8 s) is transferred to the worker, not copied.

## Caveats by runtime

- **onnxruntime-node works in worker threads** on Bun, Node and Deno (all three were measured
  here), with one model session per thread: each worker thread added about 75 MB (its own heap
  and model sessions).
- **Stop the workers before the process exits.** Node and Deno sometimes abort with `libc++abi:
  ... recursive_mutex lock failed` when the process exits while worker threads still hold
  onnxruntime sessions; awaiting `terminate()` on each worker first avoids it.
- **Bun**: `reusePort` balances only on Linux. Workers are web `Worker`s; `Bun.isMainThread` tells
  the two sides apart.
- **Node**: threads can't share a listening port; use `node:cluster` (processes) or forward from
  the main thread. A worker started from a `.ts` file needs Node's type stripping (Node 22.18+ or
  24), or point it at your built JavaScript.
- **Deno**: workers get the process's permissions unless `new Worker()` narrows them; run with the
  permissions the bot needs (`-A` in the benchmark). `Deno.serve` takes `reusePort` on Linux.
- **Pipecat** (Python): threads share the GIL, so a CPU-bound pipeline doesn't speed up on threads;
  processes do. Its model executors help because onnxruntime releases the GIL while it runs.

Durable Objects aren't measured here: on Cloudflare each call is its own Durable Object, which
Cloudflare places and isolates itself (see [Cloudflare Workers](/docs/deployment/cloudflare-workers)),
and a local workerd run doesn't show how production spreads them.

## Running it

```sh
bun install
bun run bench:concurrency --write          # about 20 minutes
bun run bench:concurrency --profile local --runtime bun,python --levels 1,25,100 --duration 4
```

The calls are in
[`tools/bench/concurrency/pipedog.ts`](https://github.com/polvallverdu/pipedog/blob/main/tools/bench/concurrency/pipedog.ts)
and
[`pipecat_concurrency.py`](https://github.com/polvallverdu/pipedog/blob/main/tools/bench/concurrency/pipecat_concurrency.py).
Each run is a fresh process; the levels go up until a series breaks, and the series take turns at
each level. Pipecat runs from the pinned upstream checkout in the same Python environment as the
[performance benchmark](/docs/performance#running-it). `--write` saves
[`tools/bench/perf/concurrency.json`](https://github.com/polvallverdu/pipedog/blob/main/tools/bench/perf/concurrency.json)
and the tables above.
